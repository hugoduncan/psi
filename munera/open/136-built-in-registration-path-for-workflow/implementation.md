- 2026-05-07 inventory: canonical built-in workflow bootstrap still passes through pseudo-extension mechanics.
  - `components/agent-session/src/psi/agent_session/workflow/bootstrap.clj` calls `ext/register-extension-in!` with `built-in:workflow` and then constructs an extension API with `ext/create-extension-api`.
  - `components/agent-session/src/psi/agent_session/workflow/core.clj` installs built-in surfaces only through that extension-shaped API: `:register-tool`, `:register-command`, `:register-prompt-contribution`, and `:on` for `"session_switch"`.
- Surface classification from the inventory:
  - tool registration: built-in `delegate` tool is installed through API callback `(:register-tool api)` in `workflow/core.clj`; storage today is extension-registry-backed via `tool-registry/register-tool-in!`.
  - command registration: built-in `delegate` and `delegate-reload` commands are installed through API callback `(:register-command api)` in `workflow/core.clj`; storage today is extension-registry-backed via `command-registry/register-command-in!`.
  - prompt contribution registration: built-in workflow prompt contribution is refreshed through runtime-state callback `:register-prompt-contribution`, which today is sourced from extension API `:register-prompt-contribution`; actual stored contributions are session prompt-contribution state keyed by `ext-path`/`id`, not extension-registry maps.
  - lifecycle hook registration: built-in workflow currently registers `"session_switch"` handler via API `(:on api)`; invocation today is extension event dispatch from `session_lifecycle.clj` through `ext/dispatch-in`.
  - active tool aggregation: `workflow/bootstrap.clj` refreshes active tools by reading `tool-registry/all-tools-in (:extension-registry ctx)` and appending those to session built-ins; `psi_tool.clj` and `tool_plan.clj` also read extension-registry-backed tool lists.
  - command lookup/dispatch: command execution paths continue to resolve commands from `command-registry/get-command-in (:extension-registry ctx)`.
  - prompt rendering/projection: built-in workflow contribution text is stored in session prompt-contribution state and therefore already shares the prompt store with extensions, but its provenance is currently written via extension-shaped API semantics using `built-in:workflow` as `ext-path`.
  - reload/session-switch lifecycle: built-in workflow relies on extension event registration for `session_switch`; namespace reload preserves command/tool surfaces because they live in extension-registry-backed storage and the current reload path preserves the extension registry during namespace reload mode.
  - introspection/resolver projections: tool and command projections in `resolvers/extensions.clj` are extension-oriented and derive exclusively from extension-registry-backed stores; prompt-contribution projection is also extension-labeled even though the underlying storage is session state.
- Tests/proofs assuming extension ownership:
  - `workflow_built_in_targeting_test.clj` reaches directly into `[:extension-registry :state :extensions built-in:workflow :tools ...]` to fetch the built-in delegate tool.
  - `workflow_reload_runtime_test.clj` and `workflow_async_path_test.clj` prove built-in command/tool behavior through extension-registry-backed query helpers (`command-registry/get-command-in`, `command-registry/command-names-in`, `tool-registry/tool-names-in`).
- Initial design implication from the inventory:
  - tool and command surfaces are the strongest candidates for shared registry reuse with explicit built-in registration entrypoints/provenance, because runtime readers already aggregate from the registry helpers and a built-in path can stay small if those helpers learn built-in ownership cleanly.
  - prompt contributions likely do not need a separate built-in store; they already live in shared session prompt-contribution state, but need built-in-specific registration provenance/entrypoints instead of extension API wrapping.
  - lifecycle hooks are the one surface that cannot remain extension-shaped if this task is to satisfy its success criteria; built-in workflow needs an explicit runtime/session lifecycle registration/invocation path rather than `ext/dispatch-in` event subscription.
- Open implementation question sharpened by inventory:
  - whether the smallest clean path is to augment shared registries with owner/provenance-aware built-in entrypoints, or to add a tiny built-in composition owner that merges built-in command/tool surfaces at read time while keeping extension registries unchanged. The inventory favors the first option for commands/tools and a dedicated built-in lifecycle path for session-switch/reload behavior.
