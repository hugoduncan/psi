# Design follow-up steps

- [x] ARCH: Make turn-augmentation registration/execution explicitly capability- and permission-gated for privileged extensions, rather than leaving manifest/permission declaration as an optional planning question.
- [x] ARCH: Require augmenter input to be a bounded core-owned projection/resolver payload, not raw `ctx`, direct atom access, or hidden runtime handles.
- [x] ARCH: Require augmentation child-session creation to route through the core/session lifecycle with canonical parent turn provenance and recursion-suppression state, not extension-local session management.
- [x] ARCH: Specify deterministic registration/invocation/result ordering for multiple augmenters so the same state and turn event produce the same recorded operations.
- [x] ARCH: Require accepted augmentation operations and diagnostics to be stored as canonical turn-scoped session/journal state consumed by pure request preparation, not only in runtime locals, extension diagnostics, or the bounded dispatch log.
- [x] AMB: Define the exact turn-augmentation input contract field set and names, including which of original user message, session metadata, effective cwd, existing session context, and turn/session ids are provided.
- [x] AMB: Define the precise turn-id creation/reuse point and lifecycle ordering around prompt submission, augmentation recording, and `prompt-prepare-request` so implementers know which event or state owns the turn id before augmentation runs.
- [x] AMB: Define how an append-context-block operation is rendered into the prepared request, including role/layer, formatting, and ordering relative to system prompt layers, extension prompt contributions, runtime metadata, conversation history, and the submitted user message.
- [x] AMB: Choose one unsupported-operation behavior for v1 augmentation results, replacing “rejected or ignored” with a single rule and diagnostic expectation.
- [x] AMB: Define partial-result semantics when one augmenter fails or when one augmenter returns a mixture of valid and invalid operations: whether valid operations from the same provider or other providers are still applied, and how this is diagnosed.
- [x] AMB: Define canceled/stale-result handling as either diagnostic recording or complete ignore, with the exact persisted state/test expectation for each case.
- [x] AMB: Define the minimum augmentation diagnostics schema/status taxonomy and query/summary surface needed to verify success, no-op, failure, unsupported operation, stale/canceled result, and replay behavior.
- [x] AMB: Define replay lookup behavior for augmentation records, including how the pre-turn phase detects replay mode for a turn and what happens when recorded operations are missing, malformed, or refer to a different turn id.
- [x] AMB: Define the concrete turn-augmenter registration API contract, including function name, argument map/function shape, return/error behavior, replacement semantics, and whether registrations are process-global, extension-scoped, or session-scoped before per-session authorization is checked.
- [x] AMB: Define the concrete augmenter result envelope, including how valid empty results, provider diagnostics, child-session ids, and operation vectors are returned so core can distinguish no-op, success, invalid, unsupported, and failed providers without inferring from ad hoc shapes.
- [x] AMB: Define the concrete core API/path an augmenter uses to launch augmentation child sessions while still receiving only the bounded turn projection as invocation input, including how parent session/turn provenance and `:suppress-turn-augmentation? true` are supplied.
- [x] AMB: Define the concrete prepared-request introspection representation for the inserted augmentation context message, replacing the illustrative `such as {:id :turn/augmentation-context ...}` with the exact layer/message/summary fields tests should assert.
