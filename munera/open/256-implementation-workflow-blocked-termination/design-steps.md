# Design review follow-ups

- [x] Define an authored, projection-compatible terminal-result topology for both `IMPLEMENTATION_COMPLETE` and `IMPLEMENTATION_BLOCKED`: the documented standalone projection reads the last declared workflow step rather than the last executed route, so two branch-specific terminal summaries cannot both be exposed by step ordering alone. Preserve the dedicated blocked handback and use an existing generic workflow contract/mechanism (or revise the design's stated mechanism) without changing generic runtime loop semantics or relying on declaration order accidentally.
- [x] Specify the canonical, deterministic `implementation.md` blocker record: exact marker/fields, who writes it, and how a later blocked summary selects the current record when prior blocked attempts exist. The design currently requires a structured-enough record but leaves its format and lookup undefined, so summaries and routing proofs would depend on heuristic interpretation.
- [x] Specify the inter-workflow status contract consumed by the new `task-lifecycle` gate: identify the exact `implement-task` yielded/structured field and exact terminal status it receives for both completed and blocked routes. The status currently belongs to `implement-pass`, while `task-lifecycle` delegates `implement-task` and can only consume the outer workflow's result; its current final summary has no pass-status output.
- [x] Reconcile the decision that `IMPLEMENTATION_BLOCKED` is authored policy parsed by the existing `workflow/pass-status-routing` operation with the referenced router: it only recognizes `IMPLEMENTATION_COMPLETE` and `MORE_WORK_REMAINS` and collapses recognized tokens to `DONE`/`REPEAT`, so it neither accepts nor distinguishes the proposed third status. State the compatible contract/mechanism and its ownership without introducing the prohibited runtime-specific blocker primitive.
