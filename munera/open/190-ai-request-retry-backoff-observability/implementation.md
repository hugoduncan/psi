# Implementation notes

2026-05-30 — Design ambiguity review: found two actionable ambiguities. The design moves retry execution to the prepared provider-request boundary but leaves the authoritative completed retry-history storage/EQL projection source underspecified, and it requires preserving active TUI/Emacs/app-runtime retry status without defining how lower-boundary retry sleep updates and clears the existing session retry projection.


2026-05-30 — Ambiguity follow-up complete: clarified that completed provider retry history is authoritative in session-owned provider telemetry captures, keyed by session/turn/provider-request/attempt and projected through EQL/`psi-tool` from telemetry rather than UI state. Also clarified active retry/backoff visibility: provider-boundary retry publishes pending delay metadata into the existing session retry projection before sleeping, preserves `:retrying`-style app-runtime/TUI/Emacs visibility, and clears active fields after retry resume or terminal outcome while telemetry remains the completed-history source.

2026-05-30 — Design inconsistency review: found three actionable inconsistencies. The design makes completed retry history authoritative in session-owned provider telemetry captures, but the referenced runtime separates HTTP provider request/reply captures from extension lifecycle events (`provider_request_started`, `provider_retry_scheduled`, `provider_request_finished`) and does not currently retain those lifecycle events as session captures for EQL projection. The design also changes attempt numbering to one-based `:attempt` while referenced telemetry contracts/code use `:retry-attempt` with first attempt `0`. Finally, the design's `provider_request_finished` final statuses (`:terminal`, `:exhausted`) conflict with the existing provider metrics telemetry contract that aggregates failures as `:status :failed` plus `:final?`/retry metadata.

2026-05-30 — Inconsistency follow-up complete: reconciled retry history with existing telemetry by making retained provider lifecycle events a separate session telemetry stream from HTTP provider request/reply captures, while keeping `/ext/provider-telemetry` dispatch for metrics/log consumers. Aligned attempt numbering to the existing zero-based `:retry-attempt` contract (`0` first execution, `1` first retry execution) and preserved metrics-compatible `provider_request_finished` statuses (`:succeeded`/`:failed`) with `:final?` plus explicit exhaustion metadata instead of new `:terminal`/`:exhausted` statuses.

2026-05-30 — Design ambiguity review: found one actionable ambiguity. The design alternates between configured maximum attempts / maximum attempt count and existing retry terminology, but the referenced runtime configuration is retry-count oriented (`:auto-retry-max-retries`); it does not explicitly define whether the configured limit includes the first provider execution attempt or only retry executions, creating an off-by-one risk for retry exhaustion and telemetry tests.

2026-05-30 — Ambiguity follow-up complete: clarified that `:auto-retry-max-retries` counts retry executions after the initial provider attempt, not total executions. Provider attempts remain zero-based via `:retry-attempt`: attempt `0` is the initial execution, retry attempts `1..N` are allowed for `N = :auto-retry-max-retries`, and a retryable failure on attempt `N` is final/exhausted rather than scheduling `N+1`.

2026-05-30 — Design inconsistency review: found two actionable inconsistencies. The design requires provider-boundary retry to preserve existing app-runtime/TUI/Emacs `:retrying` phase/status by publishing session retry fields, but referenced app-runtime status derives `:retrying` from the statechart configuration via `sc-phase-in`, while the existing statechart retrying path is also the old whole-agent-loop retry engine that the design says must not drive retries. The design also moves retry inside one prepared provider-request boundary and keys completed history by provider-request id plus zero-based `:retry-attempt`, but the referenced provider telemetry contract still requires `:attempt-id` as a unique provider execution-attempt id and current code sets it to the prepared request/turn id, leaving retry attempts under an in-place boundary retry with no unique `:attempt-id` contract.

2026-05-30 — Inconsistency follow-up complete: reconciled active retry visibility with statechart-derived UI projections by requiring provider-boundary retry to keep existing `ss/sc-phase-in`/app-runtime/TUI/Emacs surfaces reporting `:retrying` during pending backoff, while splitting that visibility from the old whole-agent-loop retry engine so provider retry resume must not dispatch `:runtime/agent-start-loop`. Also reconciled provider telemetry attempt identity: request id plus zero-based `:retry-attempt` is the canonical grouping coordinate, while `:attempt-id` remains a unique concrete provider-execution-attempt id derived from the request id and retry attempt for retried requests.

2026-05-30 — Design ambiguity review: found one actionable ambiguity. The design requires unknown provider/request failures to have an explicit default retry policy, but does not choose whether unknown failures are retryable, terminal/non-retryable, or conditionally retryable by subtype, leaving implementation and final-error/EQL semantics underspecified.

2026-05-30 — Ambiguity follow-up complete: defined unknown provider/request failures as terminal non-retryable by default. The retry boundary retries only failures that the shared provider-error classifier maps to an explicit retryable kind from observable stop reason/message/exception data/HTTP status. Classifier `:unknown` must not schedule retry; final error and telemetry/EQL should expose `:error-kind :unknown`, `:retryable? false`, and terminal/non-retryable failure reason so unknown-not-retried is distinguishable from retry exhaustion.

2026-05-30 — Design ambiguity review: found one actionable ambiguity. Provider-boundary retry introduces an in-request backoff delay, but the design does not define what happens if the user aborts/interrupts or the session is otherwise cancelled while that delay is pending: whether the sleep is cancellable, whether the next attempt is suppressed, how active retry fields are cleared, and what telemetry/final error is recorded.

2026-05-30 — Ambiguity follow-up complete: defined abort/interruption semantics for pending provider-boundary retry backoff. Pending retry delays must be cancellable by user/session abort, suppress the scheduled next provider attempt, clear active retry projection fields, preserve the retry schedule telemetry, and record a final failed/cancelled lifecycle outcome such as `:failure-reason :retry-cancelled` so cancellation is distinguishable from non-retryable terminal failure and retry exhaustion.

2026-05-30 — Design ambiguity review: found one actionable ambiguity. Streaming provider retries may occur after partial assistant text/thinking/tool-call deltas have already been emitted into the live turn/progress state, but the design does not specify whether failed-attempt partial output is discarded, hidden as transient attempt-local progress, retained for diagnostics only, or reconciled into the final transcript when a later retry succeeds.

2026-05-30 — Ambiguity follow-up complete: defined partial streaming output semantics across provider-boundary retry attempts. Failed streaming attempts keep text/thinking/tool-call deltas attempt-local: they may appear only as transient progress or clearly keyed telemetry/debug data, must be cleared/superseded before the next attempt, and must not be committed to canonical transcript/message assembly. A later successful retry owns the final assistant response and must not mix or duplicate partial output from failed attempts; failed-attempt tool calls must not execute before the normal completed-assistant-message handoff.
