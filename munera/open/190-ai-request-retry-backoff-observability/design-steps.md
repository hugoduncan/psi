# Design follow-up steps

- [x] Specify the authoritative storage/projection path for completed provider retry history: whether retry attempt records are derived from provider telemetry captures, stored under session state, or stored elsewhere; how they are keyed by session/turn/request/attempt; and which existing/new EQL resolvers expose the required session-, turn-, and request-level retry answers.
- [x] Specify how provider-boundary retry keeps active retry/backoff status visible through the existing TUI/Emacs/app-runtime session retry projection while a delay is pending, including when `:retry`, `:retry-attempt`, phase/status fields are set and cleared, and whether this replaces or preserves the old statechart retry state.
- [x] Reconcile completed retry-history storage with the existing provider telemetry split: specify whether `provider_request_started` / `provider_retry_scheduled` / `provider_request_finished` lifecycle events are retained under session state as new telemetry captures, how that differs from existing HTTP provider request/reply captures, and which retained records EQL projects from.
- [x] Align retry attempt numbering with the referenced telemetry contract/code: either keep `:retry-attempt` zero-based with first attempt `0`, or explicitly update the provider telemetry contract, metrics aggregation, existing resolvers, and UI projections to the new one-based `:attempt` semantics.
- [x] Align `provider_request_finished` failure status semantics with the existing provider metrics telemetry contract: either preserve `:status :failed` plus `:final?`/exhaustion metadata, or explicitly update the metrics/event contract and all consumers to understand `:terminal` and `:exhausted` statuses.
- [x] Clarify retry limit semantics at the provider-request boundary: specify whether the configured retry limit counts total provider execution attempts or only retry executions, map that explicitly to the existing `:auto-retry-max-retries` / retry policy fields, and state the expected attempt numbers and exhaustion point for first attempt plus retries.
- [x] Reconcile active retry phase/status with existing statechart-derived UI projections: specify whether `sc-phase-in` / app-runtime/TUI/Emacs status should derive `:retrying` from provider-boundary active retry fields, or whether the statechart `:retrying` state will be retained without executing the old whole-agent-loop retry resume path.
- [x] Reconcile provider telemetry execution-attempt identity for provider-boundary retries: specify how required `:attempt-id` remains unique per provider execution attempt when retries occur inside one prepared request, or explicitly update the provider telemetry/metrics/resolver contract to use `provider-request-id` plus zero-based `:retry-attempt` as the attempt coordinate.
- [x] Define the default policy for unknown provider/request failures at the retry boundary: specify whether unknown failures are retried, treated as terminal/non-retryable, or split by observable subtype, and state the expected final error and retry telemetry/EQL classification for that default.
- [x] Define abort/interruption semantics for pending provider-boundary retry backoff: specify whether user/session cancellation interrupts the delay and prevents the next provider attempt, how active retry projection fields are cleared, and what final telemetry/error shape records the cancelled retry.
- [x] Define partial streaming output semantics across retry attempts: specify whether text/thinking/tool-call deltas emitted by a failed streaming attempt before a retryable error are discarded, surfaced only as attempt-local/transient progress, retained only in telemetry/debug captures, or merged into transcript state; ensure a successful later retry cannot duplicate or mix partial output from failed attempts.
- [x] Specify the concrete provider request identity field carried by lifecycle telemetry and EQL projections: whether provider retry events must include an explicit `:provider-request-id`, whether it is always equal to `:turn-id` for prepared requests, or whether EQL derives `:psi.provider-request/id` from `:turn-id`; update the event payload/resolver contract so grouping by provider request is unambiguous.
- [x] Reconcile pending-backoff cancellation telemetry with the provider telemetry cardinality contract: specify whether cancellation emits a distinct request-level final/cancel event, updates `provider_request_finished` to allow non-attempt request finals, or records cancellation another way, while preserving that `provider_request_finished` remains exactly once per actual provider execution attempt unless the contract is explicitly changed.
- [x] Clarify provider retry header handling at the provider-request retry boundary: specify whether retry scheduling must honor existing provider error headers such as `Retry-After` / rate-limit reset when computing backoff, how those headers are carried from streaming/non-streaming provider failures into retry metadata, and how `:delay-source` / delay telemetry should distinguish header-derived delay from configured exponential backoff.
- [x] Define the caller-visible final error data contract for provider-boundary retry outcomes: specify which fields on the assistant error message and/or execution result distinguish terminal non-retryable, retry-exhausted, and retry-cancelled outcomes; how the last provider cause, error kind, HTTP status, retryable flag, attempt count, and failure reason are preserved; and what focused tests assert without relying only on prose error text.
- [x] Clarify how the existing `:auto-retry-enabled` session flag gates provider-boundary retry: specify whether disabled retry performs classification only, whether any `provider_retry_scheduled` or active retry/UI projection is emitted, what structured final `:failure-reason` / `:retryable?` / `:max-retries` fields report for a retryable failure when retry is disabled, and how this differs from `:auto-retry-max-retries 0`.
- [x] Reconcile the caller-visible final error `:failure-reason` enum with disabled retry semantics: either include `:retry-disabled` in the final error contract and outcome-specific requirements, or map disabled retry to one of the existing provider-boundary outcome reasons without contradicting the `:auto-retry-enabled false` section.
