# Design follow-up steps

- [x] A1: Specify the merged `design-review` step's shared session config explicitly as the union required by the three current review prompt frontmatters (`read`, `bash`, `edit`, `write`; `work-independently`, `review-task-architecture`, `task-design`). Prompt-group `:prompt-workflow` imports only markdown bodies under 226, so relying on the existing per-prompt frontmatter would drop the review skills/tools when the three phases move under one multi-prompt step.
- [x] B1: Specify the exact merged topology and route map, including the single follow-up step name and where the pass-loop bound lives. The design should make it unambiguous that `design-review` routes `DONE` to `final-summary` and `REPEAT` to the design-profile follow-up, and that the follow-up routes back to `design-review` with `:max-iterations 6` on the transition targeting `design-review` (or an explicitly equivalent mechanism) so the current “at most six total review passes” bound is preserved rather than accidentally limiting follow-up entries.
- [x] B2: Clarify the concrete prompt-body changes required to satisfy the “design + architecture sources are assembled once (turn 1)” acceptance criterion. In particular, state that the first `architecture` prompt must explicitly load `design.md` and the needed architecture sources into the shared session, and that the later `ambiguity`/`inconsistency` prompts should rely on that shared context except for targeted re-reads when something is missing or stale.
- [x] B3: Clarify how the single post-batch `design` follow-up identifies the items it should execute. The design should state that “the preceding review pass” means the whole three-prompt `design-review` batch, so the follow-up executes all unchecked items newly added by the architecture, ambiguity, and inconsistency prompts in that batch while leaving pre-existing unchecked items untouched; specify whether `review-follow-up-design.md` wording/context must change to make that unambiguous.
- [x] C1: Resolve the routing-status validation inconsistency in the merged topology. `design.md` currently claims the merged `design-review` judge can reuse existing `workflow/pass-feedback-routing` and route `DONE` only when all three prompt replies returned `REVIEW_COMPLETE`, but the existing operation only detects `ACTIONABLE_FEEDBACK` and otherwise returns `DONE`; the current unmerged workflow relies on each phase's separate `pass-status-routing` judge to reject missing, malformed, duplicate, or disallowed `PASS_STATUS` lines before `clarity-status`. Specify either a change to `pass-feedback-routing`/a new deterministic operation that validates every per-prompt reply against `ACTIONABLE_FEEDBACK|REVIEW_COMPLETE`, or an equivalent explicit validation mechanism compatible with one post-drain multi-prompt judge.
- [x] C2: Update design.md's Status/Depends-on wording now that task 226 has landed. The current design still says 227 is ready only once 226 lands and warns not to plan/implement before 226's grammar is real, but the repository now has the multi-prompt grammar/docs from closed 226; make the dependency status reflect that the prerequisite is satisfied while preserving that 227 adds no new runtime capability.
- [ ] D1: Specify how the single `design-follow-up` step identifies the unchecked `design-steps.md` items newly added by the immediately preceding three-prompt batch. The current design gives `design-follow-up` only `:prompt-workflow "review-follow-up-design.md"`, but its semantics require distinguishing batch-added unchecked items from pre-existing stale unchecked items; make the mechanism unambiguous (for example by passing the three per-prompt review replies or a deterministic newly-added item list into the follow-up context, or by explicitly defining a git/task-file evidence rule and the uncertainty behavior).
