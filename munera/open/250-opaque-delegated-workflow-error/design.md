# Actionable delegated-workflow failure diagnostics

> Auto-generated by the context-manager post-turn tooling-friction analyzer (task 239). Design review has refined the task; human approval is still required before planning or implementation.

## Goal

When a workflow `:delegate` step fails because its child workflow failed, expose a safe, deterministic explanation of the child failure instead of only `"Delegated workflow failed"`. Preserve all existing workflow status, retry, blocking, cancellation, and result semantics.

## Problem and root cause

A failed delegated run currently loses diagnostics along two distinct paths:

1. **Attempt execution failure:** the failed child's terminal step attempt may contain an actionable `:execution-error`. `delegate-run-runtime-result` does not select that attempt and falls back to `{:status :failed}`, so the parent delegate attempt records only the generic message.
2. **Terminal-outcome-only failure:** `delegate-run-runtime-result` retains the child's `:terminal-outcome` in the parent failure payload's `:details`, but `workflow-execution/execution-result` reduces the parent attempt to its generic `:message`, and `run-failure-error` renders that message instead of the retained terminal diagnostic.

Thus attempt diagnostics are lost during delegate normalization, while terminal diagnostics survive normalization but are lost during public projection. Both produce a failed parent with a nil result and an opaque public error.

## Authoritative path and ownership

The authoritative path is:

1. The persisted child workflow run supplies canonical failure state through its ordered step attempts and `:terminal-outcome`.
2. The workflow-runtime delegate-step boundary normalizes that state into one delegated-failure envelope and records it as the parent delegate attempt's `:execution-error`.
3. The agent-session workflow execution facade selects the parent run's terminal step/latest terminal attempt and forwards its canonical envelope without reconstructing or inspecting child state.
4. `psi.workflow/execute-run` renders the envelope's `:message` as `:psi.workflow/error`. The synchronous registered `delegate` tool projects the same string as provider-visible `Error: ...` text; asynchronous completion surfaces carry the same error.

The workflow-runtime delegate-step boundary is the sole owner of child-failure selection and normalization. Agent-session mutations, the registered tool, RPC, TUI, and other adapters may project or render the envelope, but must not inspect child sessions, transcripts, provider payloads, or child runs to create competing failure semantics.

The structured acceptance boundary for the reported `:error`/`:result` behavior is the `psi.workflow/execute-run` mutation result. End-to-end proof must additionally inspect the registered synchronous `delegate` tool's provider-facing result to ensure that adapter projection does not replace the actionable message.

## Canonical delegated-failure envelope

A failed child run produces this parent attempt `:execution-error` shape:

```clojure
{:reason :delegated-workflow-failed
 :message <bounded public message>
 :delegate-failure
 {:source <one of :execution-error, :terminal-outcome, :fallback>
  :run-id <direct child run id>
  :target <delegated workflow name>
  :reason <optional safe keyword>
  :step-id <optional selected child step id>
  :attempt-id <optional selected child attempt id>
  :nested-cause <optional immediate delegated-failure identity>}}
```

`:source`, `:run-id`, and `:target` are required in every persisted `:delegate-failure`. `:reason` is present only for a safe reason keyword, `:step-id` and `:attempt-id` are present only for valid nonblank string identities, and `:nested-cause` is present only for a recognized immediate envelope. An unavailable or invalid optional value is represented by omission; these keys are never persisted with nil values.

The outer `:delegate-failure :reason` has exactly one source for each `:source`; candidates are never merged or used as fallbacks for one another. For `:source :execution-error`, it is the selected attempt's outer `:execution-error :reason` when that value is safe. This remains true when the selected error is a canonical delegated-failure envelope: the new outer reason is then `:delegated-workflow-failed`, while the immediate inner reason may appear only under `:nested-cause`. For `:source :terminal-outcome`, the outer reason is the selected child `:terminal-outcome :reason` when safe. For `:source :fallback`, `:reason` is always omitted. A missing or unsafe source-specific reason is omitted without changing the selected source or consulting another reason field.

`:nested-cause`, when present, contains only the immediate nested envelope's allowlisted `:run-id` and `:target`, plus `:reason`, `:step-id`, and `:attempt-id` only when each value satisfies the same rule as the parent envelope. It never embeds another `:nested-cause` or causes traversal of another run.

A selected execution error is a canonical immediate nested envelope only when its outer `:reason` is exactly `:delegated-workflow-failed`, its `:message` is a nonblank string no longer than 512 Unicode code points, and its `:delegate-failure` is a map containing a valid `:source` plus nonblank string `:run-id` and `:target`. A valid `:source` is one of `:execution-error`, `:terminal-outcome`, or `:fallback`; `:step-id` and `:attempt-id` are optional nonblank strings, and `:reason` is an optional safe reason keyword as defined below. For a canonical immediate envelope, `:nested-cause :reason` comes from the inner `:delegate-failure :reason`, never from the outer `:execution-error :reason`; all identity fields likewise come from that same immediate inner map. Nil optional fields are omitted, its `:nested-cause` and every non-identity field are ignored, and no descendant run is read.

If any required nested-envelope field is absent or invalid, the child execution error is not treated as nested metadata: its message is sanitized as an ordinary untrusted execution message and `:nested-cause` is omitted. An invalid optional identity field is omitted without invalidating otherwise canonical immediate metadata. Even a structurally canonical nested message passes through the same idempotent sanitization steps 1–4 again before the outer envelope uses it; nested metadata never creates a bypass. This preserves useful safe text while ensuring partial or malformed metadata cannot supply identity or weaken normalization.

Only these allowlisted fields cross the child-parent boundary. Arbitrary exception data, raw stack traces, `ex-data`, operation results/details, candidate-failure payloads, judge output, last-result text, provider request/response data, session identifiers, and transcript content do not.

### Public message normalization

The envelope's `:message` is produced once at normalization time and is the only envelope field rendered into `:psi.workflow/error` or provider-facing tool text. The canonical fallback is exactly `"Delegated workflow failed"`.

A **safe reason keyword** is a keyword read only from the selected execution error's `:reason`, the child `:terminal-outcome :reason`, or a recognized immediate `:delegate-failure :reason`. Its body (`name` or `namespace/name`, without the leading colon) must match `[A-Za-z0-9][A-Za-z0-9._-]*(/[A-Za-z0-9][A-Za-z0-9._-]*)?` and contain at most 64 characters; rendering prepends exactly one colon (for example, `:iteration-limit-reached`). Other values are omitted rather than stringified. The only terminal numeric metadata permitted is `:iteration-count` and `:max-iterations`; each is rendered only when it is an integer from 0 through `Long/MAX_VALUE`. No other terminal-outcome field contributes text.

An execution-error message is eligible only when its raw `:message` is a nonblank string and its result after steps 1–4 is actionable. Non-string and blank messages are ineligible. A redactable message remains eligible when safe letters or digits remain outside the placeholders (for example, `token=abc123 request rejected`); a message that becomes placeholders only is ineligible. An ineligible execution-error message does not force the generic fallback: selection continues to an actionable terminal outcome before falling back. For an eligible execution-error source, the sanitized message is the cause text.

For a terminal-outcome source, the exact cause text is `terminal outcome <printed-reason>` followed by ` (iteration <iteration-count> of <max-iterations>)` only when the reason is `:iteration-limit-reached` and both permitted counts are present. A terminal outcome without a safe reason is not actionable and falls back.

Sanitize the target, selected step, and candidate cause separately with steps 1–4 below, using the resulting cause actionability to determine execution-error eligibility, then assemble and bound the public message with steps 5–6:

1. Remove NUL and every Unicode control code point except whitespace.
2. Scan left to right, replacing non-overlapping sensitive spans in this precedence: stack frame, credential pair, bearer/prefixed token, then path. At each position, the first matching category wins. A replacement consumes only the defined span; punctuation immediately before or after it remains unless that punctuation is explicitly part of the span below.
   - A stack-frame span starts with case-sensitive `at` whose left boundary is start-of-string or a character other than a Unicode letter, digit, or `_`; it is followed by one or more ASCII space or tab characters, then a nonempty Java/Clojure symbol made of Unicode letters or digits plus `.`, `_`, `$`, `/`, or `-`, and ends with one parenthesized location containing no whitespace or parentheses and a colon plus one or more ASCII digits immediately before the closing parenthesis; for example, `at child.core/run(child.clj:42)`. The entire span from `at` through the closing `)` becomes `[STACKTRACE_REDACTED]`; adjacent leading `(`, trailing `,`, or trailing `.` remains.
   - A credential-pair span begins at a case-insensitive ASCII key token delimited on the left by start-of-string or a character other than an ASCII letter, digit, `_`, or `-`. The key is one or more ASCII letters, digits, `_`, `.`, or `-` and must contain `token`, `secret`, `password`, or `credential`, or contain `api-key` or `api_key`. After optional ASCII spaces or tabs, the separator is exactly one of `=>`, `=`, or `:` (longest match first), followed by optional ASCII spaces or tabs. The value is either a single- or double-quoted string, consuming through the matching quote with backslash escaping the next code point, or an unquoted run ending before whitespace or `,`, `;`, `)`, `]`, or `}`. The complete key, separator, and value become `[REDACTED]`; surrounding delimiters remain. An unterminated quoted value, or a missing or empty value, does not match.
   - A bearer-token span is case-insensitive `Bearer`, delimited on the left like a credential key, followed by one or more ASCII spaces or tabs and an unquoted token of at least 8 ASCII letters, digits, `.`, `_`, `~`, `+`, `/`, or `-`, optionally ending in up to two `=` padding characters. The entire scheme and token become `[REDACTED_TOKEN]`. A standalone prefixed-token span is `sk-` or `pk-` (case-insensitive), delimited on the left by start-of-string or a character outside the token alphabet, followed by at least 8 characters from the same token alphabet; it ends before the first character outside that alphabet. For either token form, trailing `.` characters are excluded as sentence punctuation, while dots before the final character remain part of the token. The entire prefixed token becomes `[REDACTED_TOKEN]`. Quotes and adjacent sentence punctuation remain.
   - A path span is unquoted and delimited on the left by start-of-string or whitespace, `(`, `[`, `{`, `=`, `:`, `,`, or `;`. It begins with `/`, `~/`, `./`, `../`, an ASCII drive letter followed by `:\\` or `:/`, or two leading backslashes, and ends before whitespace or `,`, `;`, `)`, `]`, `}`, single quote, or double quote. If the captured run ends in `.`, `:`, `!`, or `?`, those trailing punctuation characters are excluded from the span. Any such absolute, home-relative, dot-relative, drive, or UNC span becomes `[PATH_REDACTED]`. A different relative run must contain at least one `/` or `\\`, uses the same left and right delimiters, and is redacted only when its segments include, case-insensitively, a segment containing `secret`, `token`, `password`, or `credential`, or a segment exactly `.ssh` or `id_rsa`.
3. Convert every whitespace run, including line breaks and tabs, to one ASCII space and trim leading/trailing whitespace.
4. A sanitized component is actionable only if text outside the four placeholders `[STACKTRACE_REDACTED]`, `[PATH_REDACTED]`, `[REDACTED]`, and `[REDACTED_TOKEN]` contains a Unicode letter or digit. A non-actionable execution-error candidate is ineligible and selection continues to the terminal outcome; use the fallback and `:source :fallback` only if no actionable candidate remains.
5. Escape each backslash and apostrophe in the sanitized target and step with a preceding backslash. Format an actionable cause exactly as `Delegated workflow '<target>' failed at step '<step>': <cause>` when the sanitized step is actionable under step 4, or `Delegated workflow '<target>' failed: <cause>` otherwise. The direct delegated target is required by this boundary; if it is not actionable under step 4, use the fallback.
6. If the formatted message exceeds 512 Unicode code points, retain its first 496 code points and append the exact 16-character marker ` ... [truncated]`. Thus the persisted canonical message, including its marker, is never longer than 512 code points. Redaction and whitespace normalization always precede truncation, so truncation cannot reveal a partial secret or create a second normalization result.

Examples that define the observable contract:

- Target `child-flow`, step `build`, and cause `tool timed out` produce `Delegated workflow 'child-flow' failed at step 'build': tool timed out`.
- Terminal reason `:iteration-limit-reached` with counts 4 and 4 produces cause `terminal outcome :iteration-limit-reached (iteration 4 of 4)` before the same target/step prefix is applied.
- A message containing only `at child.core/run(child.clj:42)` falls back after the sole stack frame becomes a placeholder; `(at child.core/run(child.clj:42)), retry` becomes `([STACKTRACE_REDACTED]), retry`.
- `token="abc 123", request rejected` becomes `[REDACTED], request rejected`; `Authorization: Bearer abcdefgh.` becomes `Authorization: [REDACTED_TOKEN].`; `sk-abcdefgh, denied` becomes `[REDACTED_TOKEN], denied`.
- `open /home/alice/private.edn, then retry` becomes `open [PATH_REDACTED], then retry`; `read config/secret-store.edn.` becomes `read [PATH_REDACTED].`. By contrast, `token=abc123 request rejected` remains actionable as `[REDACTED] request rejected`, while `token=` is unchanged because it has no value.

## Deterministic cause selection

For a child whose status is `:failed`:

1. Select the terminal child step by `:terminal-outcome :step-id` when it names a real child step; otherwise use the child's `:current-step-id` when valid; otherwise choose the last step in effective `:step-order` whose latest attempt has `:status :execution-failed`. Do not depend on map iteration order.
2. Within that step, select the attempt named by `:terminal-outcome :attempt-id` when it belongs to the step; otherwise select the latest attempt in its ordered attempt vector.
3. If that selected attempt's `:execution-error :message` is a nonblank string, sanitize it through public-message steps 1–4. Choose it and set `:source :execution-error` only when the sanitized result is actionable. Non-string, blank, and sanitized-nonactionable messages are ineligible; redactable messages with remaining actionable text are eligible. Earlier failed retry attempts are history and cannot override the terminal attempt.
4. When the selected execution-error message is ineligible or absent, if `:terminal-outcome` has a safe reason, render its allowlisted fields and set `:source :terminal-outcome`.
5. Only when neither candidate is actionable, or when the required target is non-actionable after sanitization, use `:source :fallback` and the generic fallback message.

If the selected execution error is a canonical delegated-failure envelope, re-sanitize its bounded message and copy only its immediate allowlisted identity into `:nested-cause`. Do not recursively unwrap envelopes or traverse descendant runs. This keeps selection deterministic and bounded while preserving actionable nested context.

## Parent-visible failure contract

After propagation:

- The child remains `:failed`.
- The parent delegate attempt remains `:execution-failed`, and the parent workflow remains `:failed` after retries are exhausted.
- Existing retry policy still decides whether the parent delegate step is attempted again; a superseded attempt's error is not selected as the terminal public cause.
- Failure produces no accepted result. `psi.workflow/execute-run` continues to return `:psi.workflow/result nil`.
- `:psi.workflow/error` equals the canonical terminal parent attempt envelope's `:message`; projection must select the terminal step/latest terminal attempt rather than the first historical step error.
- If `psi.workflow/resume-run` resumes a blocked run that then fails at a delegate step, it returns that same terminal-attempt message in `:psi.workflow/error`, using the same terminal step/latest terminal attempt selection so pre-resume and superseded retry history cannot win. The resume mutation retains its existing response shape and does not acquire a `:psi.workflow/result` field.
- The synchronous registered `delegate` tool renders `Error: <same message>` and does not synthesize a success result.
- The async completion record's `:error` and background-job payload's `:error` each equal the canonical message. Notification text embeds that message unchanged exactly once as `Workflow '<workflow-name>' <status>: <message> (run <run-id>)`; append-entry text embeds it unchanged exactly once in the heading `Workflow '<workflow-name>' — <status>: <message> (run <run-id>)`, before any existing optional result section. The wrapper text is not itself subject to the 512-character envelope bound, and no projection re-sanitizes or otherwise normalizes the message.
- Blocked children remain blocked delegation outcomes, and cancelled or removed children retain their existing cancellation/removal messages. This task does not reclassify those outcomes as failed-child diagnostics.

## Scope

### In scope

- Normalize failed-child diagnostics at the workflow-runtime delegate-step boundary.
- Preserve the envelope on the canonical parent attempt and project its message through execute/resume and registered-delegate surfaces.
- Cover both currently distinct diagnostic-loss paths.
- Add boundedness, redaction, deterministic selection, nested-failure, and fallback proof.

### Out of scope

- Changing workflow statecharts, statuses, retry policy, blocking, cancellation, removal, retention, or successful result/yield behavior.
- Surfacing raw stack traces, arbitrary child payloads, transcripts, provider data, or session internals.
- Introducing adapter-specific child-run inspection or a second failure-normalization contract.
- Changing unrelated top-level workflow failure wording except where needed to faithfully project a delegated-failure envelope.

## Acceptance criteria

1. A child terminal attempt with an execution error records a parent delegated-failure envelope with `:source :execution-error`, stable direct-child/step/attempt identity, the safe selected outer execution-error reason when available, and a specific safe message; a canonical immediate nested envelope keeps `:delegated-workflow-failed` as that outer reason and carries its distinct inner reason only in `:nested-cause`. The execute mutation returns `:failed`, nil result, and that message rather than the generic fallback.
2. A child with a terminal-outcome-only failure records `:source :terminal-outcome`; its safe terminal reason is the outer envelope reason and its terminal step is visible in the execute mutation error. This proves that retained terminal details survive public projection.
3. A failed child with no safe actionable cause records `:source :fallback`, omits the outer reason, and exposes exactly `"Delegated workflow failed"`.
4. When retries exist, only the selected terminal step's terminal/latest attempt determines the cause; earlier failed attempts cannot win. Selection is independent of map iteration order.
5. A canonical nested delegated failure reuses the immediate sanitized message and copies identity from the immediate inner `:delegate-failure`; malformed or partial nested metadata cannot contribute identity, weaken sanitization, trigger recursive run traversal, or embed recursive metadata.
6. Public messages follow the exact prefix, terminal rendering, allowlists, redaction order, lexical match boundaries, fallback rule, and ` ... [truncated]` bound above. Table-driven tests cover positive and negative delimiter cases, adjacent punctuation, quoted and unquoted credentials, token minimum lengths, every named path family, secret-bearing relative paths, stack frames, placeholder-only fallback, and the 512-code-point boundary. Disallowed exception, operation, provider, session, transcript, judge-output, and last-result fields are absent from the parent envelope.
7. The registered synchronous `delegate` tool exposes `Error: <the same actionable message>` at its provider-facing result boundary. Async completion/background-job `:error` fields equal that message; notification and append-entry text embed it unchanged in their existing context wrappers.
8. Existing successful, blocked, cancelled, removed, retry, and result behavior remains unchanged; focused regression tests and the relevant workflow/agent-session suites pass.
9. When a blocked run is resumed and then terminalizes with a delegated failure, `psi.workflow/resume-run` returns `:failed` and the selected canonical terminal-attempt message in `:psi.workflow/error`; pre-resume or superseded retry errors cannot win, and the mutation still has no `:psi.workflow/result` field.
