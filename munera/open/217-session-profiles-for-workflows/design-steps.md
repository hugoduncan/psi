# Design follow-up steps

- [x] AR1: Specify that `/session-profile` and `/session-profiles` are added through the backend single-source built-in command specs and existing slash-command dispatch path, with profile selection mutating canonical session state through existing dispatch/mutation patterns and profile reads exposed via EQL resolvers; no adapter-local profile lists or direct state/atom writes.
- [x] AR2: Refine workflow snapshot semantics so top-level runs persist a canonical effective profile-definition/resolved-profile snapshot on workflow-run state, while delegate steps pass profile-derived concrete model/thinking/speed/effort through the existing narrow `:inherited-defaults` snapshot; do not widen `:inherited-defaults` to include profile maps or require nested runs to re-read mutable user/project config to resolve profile names.
- [ ] AMB1: Resolve config merge ownership for `:agent-session :session-profiles`: either change effective user/project `:agent-session` resolution to deep-merge profiles across user → project-shared → project-local, or specify a profile-specific resolver that deep-merges only `:session-profiles`; make the chosen rule explicit relative to current non-profile config merge behavior.
- [ ] AMB2: Pin the exact supported session-profile key set for this task. Either explicitly limit profiles to `:model-provider`, `:model-id`, `:thinking-level`, `:speed-mode`, and `:effort-override`, or list any additional supported model-invocation/session keys and their precedence/materialization behavior.
- [ ] AMB3: Define invalid and partial profile behavior: missing only one of `:model-provider`/`:model-id`, unknown provider/model ids, invalid thinking/speed/effort values, and profiles that resolve to no concrete settings. Specify whether `/session-profiles` lists them, whether `/session-profile <name>` applies valid fields partially, fails atomically, or ignores invalid fields, and what error text must include.
- [ ] AMB4: Define live-session persistence semantics when `/session-profile <name>` applies concrete settings and when `/session-profile clear` clears metadata: which fields are journaled or survive resume/fork/new-session inheritance, whether selected-profile metadata is journaled, and whether speed/effort remain session-transient like the existing `/speed` and `/effort` commands.
- [ ] AMB5: Pin workflow grammar placement and applicability for `:session-profile`: whether it is accepted only as a top-level target-authored session-config entry, also inside legacy/nested `:session` maps or markdown frontmatter, and which step forms (`:session`, `:delegate`, LLM judge, `:invoke`) may carry `:session-profile` plus concrete profile-affecting overrides. Also state where the key lives in canonical IR/effective step state.
