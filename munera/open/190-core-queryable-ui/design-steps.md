# Design follow-up steps

- [x] Define the concrete adapter-to-core capability provider contract for deriving `:psi.ui/...` capability/action data on demand, including where it is installed in runtime context, what function/data shape it returns, and how missing/errored providers map to headless/unavailable EQL results.
- [x] Specify the authoritative invocation route for action descriptors when generic invocation is optional: whether extensions invoke a Pathom mutation, dispatch event, RPC/frontend-action request, or only present the descriptor in this slice, and how `:emacs-command` invocation data reaches Emacs without extension frontend coupling.
- [x] Align the make-visible capability vocabulary in `design.md` so all examples and extension-usage guidance use the single resolved namespaced keyword `:psi.ui.capability/make-visible` (or explicitly mark any shorthand as non-normative), avoiding a second `:ui.capability/make-visible` contract.
- [x] Define exact unsupported/headless/provider-error return semantics for `:psi.ui/actions` and `:psi.ui/make-visible-action`: whether the convenience attr returns `nil` or an unavailable descriptor, which reason/diagnostic fields are required, and when `:psi.ui.capability/make-visible` is absent versus present with an unavailable action.
- [x] Specify the concrete UI action request contract if side-effecting invocation is implemented in this slice: the exact dispatch event name, required payload keys (action id, invocation data, session/runtime correlation), extension-facing submission API, and acknowledgement/error result shape; otherwise explicitly mark invocation as descriptor-only and create the follow-up task.
- [x] Align `design-decisions.md` with `design.md` for unavailable make-visible semantics: `:psi.ui/make-visible-action` always returns a descriptor, unavailable reasons are `:psi.ui.unavailable.reason/...` keywords, and unavailable descriptors include `:psi.ui.action/unavailable-message`.
- [x] Define active UI/session identity for runtime-scoped make-visible discovery: how the provider chooses the active UI/buffer/session when the resolver has no session-id input, whether descriptor invocation data includes session/runtime correlation, and how this aligns with Emacs/RPC focus-session state.
- [x] Specify provider output normalization and validation rules: required versus defaultable fields, descriptor validation, serialisability checks, unknown invocation-kind handling, and which invalid shapes become `:psi.ui.unavailable.reason/provider-error` versus normalized unavailable/headless data.
- [x] Align `resolved-design-questions.md` with the current unavailable make-visible contract: `:psi.ui/make-visible-action` always returns a descriptor, and unavailable descriptors are not merely optional diagnostics.
- [x] Define canonical `:psi.ui/actions` membership semantics for unavailable make-visible descriptors: whether the general actions collection contains only currently available actions or may include unavailable descriptors, and align all missing/no-attached/unsupported/provider-error cases to that rule.
- [x] Specify provider coherence rules between `:psi.ui/capabilities` and `:psi.ui/actions`: whether every available action's capability must be present, whether every advertised capability needs at least one available action descriptor, and how make-visible mismatches are normalized or treated as provider-error.
- [x] Align model ownership wording in `design.md`: the UI capability/action model is core/runtime-owned as a query/provider contract, but advertised capabilities/actions are derived on demand and must not be stored or cached in root state.
- [x] Define the UI capability provider installation and lifetime contract for adapter-owned UI attachment state: when RPC/Emacs and TUI install or update the runtime-context provider, how a provider can access connection/UI-state that is created after the agent-session ctx, how detach/shutdown maps back to no-provider/no-attached-UI semantics, and how the single-active-UI rule is enforced if more than one adapter/connection could install a provider.
