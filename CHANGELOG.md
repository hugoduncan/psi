# Changelog

All notable user-visible changes to psi are documented here.
Format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/).
Version scheme: `MAJOR.MINOR.PATCH` where PATCH = `git rev-list HEAD --count` at release time.

## [Unreleased]

### Added
- Added Claude Opus 5 (`claude-opus-5`) as a selectable built-in Anthropic model: adaptive-thinking, image + text input, native JSON-Schema structured output, and mid-conversation system-message support. Select with `/model anthropic claude-opus-5`. Pricing/context-window/max-tokens mirror Claude Opus 4.8 as placeholders pending official Anthropic publication.
- Documented a DeepSeek `models.edn` custom-provider example (`doc/custom-providers.md`) for `deepseek-v4-flash` via DeepSeek's Anthropic-compatible endpoint (`https://api.deepseek.com/anthropic`), using psi's existing `:anthropic-messages` custom-provider transport. Custom Anthropic-compatible providers can now declare `:adaptive-thinking true` on a model to opt into Anthropic's adaptive `output_config.effort` thinking-request shape instead of the classic `budget_tokens` shape — previously only reachable by built-in catalog models.
- Custom `models.edn` model definitions can now declare `:supports-mid-conversation-system-messages true|false` to opt into the agent-session mid-conversation system-message capability (`:session/inject-mid-system-message`). The field defaults to `false` for `:anthropic-messages` custom providers (the capability inference is built-in-only — only built-in `:openai`/`:openai-completions` catalog models get it inferred from the runtime API shape), and the docs advise setting it only after verifying the endpoint honours per-turn `system` changes.
- Three GPT-5.6 Codex-supported model variants — `gpt-5.6-sol`, `gpt-5.6-terra`, and `gpt-5.6-luna` — are now available in the built-in model catalog and selectable via `/model`, RPC `set_model`, and the RPC/TUI model pickers. Each offers reasoning, image + text input, a 272K-token context, and native JSON-Schema structured output over the Codex path; the three differ only in pricing tier (sol > terra > luna). Under OpenAI OAuth each variant is routed at turn preflight to the ChatGPT/Codex backend with its id sent verbatim (confirmed by live streaming probe), the same path already used by `gpt-5.5`. Bare `gpt-5.6` remains unsupported under OpenAI OAuth.

### Fixed
- An OAuth request to the `:anthropic-messages` transport that gets an HTTP 400 (and retries with compatibility fallbacks) now keeps its OAuth betas (`oauth-2025-04-20`, `claude-code`, `context-management`, `prompt-caching-scope`) on the retried request, stripping only `interleaved-thinking`: the `:without-all-betas` fallback decision (which preserves the OAuth betas and clears them only for non-OAuth requests) now reads the transport's computed `oauth?` flag through the namespace that actually sets it (`psi.ai.providers.anthropic`), not the helper namespace that wraps the 400 handler — a namespaced-keyword drift that stripped ALL betas (including the OAuth ones) from the retried request, which a full-suite run caught via the OAuth 400-retry test.
- A truncated Anthropic streamed turn (the SSE body EOFs mid-block — a `content_block_start` with no matching `content_block_stop`, e.g. a non-conforming/truncated Anthropic-compatible endpoint) now closes the open block before the terminal `:done`: `stream-anthropic` tracks open content-block indices and `emit-terminal-done!` (shared by the `message_stop` terminal and the EOF-level flush) emits the matching `:toolcall-end`/`:thinking-end`/`:text-end` for each open index before the `:done`, so the turn accumulator never finalizes with an OPEN block index. The `:openai-completions` transport received the same fix at its EOF flush — a `tool_calls` delta chunk followed by EOF (no `finish_reason`, no `[DONE]`, no usage chunk) now closes the open tool call with `:toolcall-end` before the `:done` (reusing the same `force-start-pending-chat-tools!`/`emit-chat-tool-ends!` helpers the finish-reason branches use; a not-yet-started fragment is force-started so it is balanced). The codex transport already balanced open tool indexes at its EOF flush; all three transports now emit no unbalanced or open block events at the terminal.
- A `:anthropic-messages` stream whose first event is a content-block event (`content_block_start`/`content_block_delta`/`content_block_stop` — a malformed/non-conforming stream that never sends `message_start`) now emits `:start` before the first content event, matching the `:openai-completions` and `:openai-codex-responses` transports: previously `:start` appeared only at the terminal, AFTER the content events. And `content_block_delta`/`content_block_stop` events for an UNKNOWN index (no prior `content_block_start` — a stream that omits start events, reuses indices, or reorders deltas/stops ahead of starts) are now skipped instead of emitting unbalanced phantom `:text-delta`/`:text-end` for a block that never had a `:text-start` (the turn accumulator's `note-content-delta!` previously opened a block at an unbegun index). The `:start`-once emitter is now a single shared `request-support/emit-start!` used by all three transports (was three byte-identical per-transport copies — the review-14 triplication class).
- A turn context that receives its terminal event (`:turn/done`/`:turn/error`) as the FIRST event — before any `:turn/start` — now terminates correctly instead of silently dropping it: the turn statechart's initial `:idle` state previously accepted only `:turn/start`, so a direct `create-turn-context` consumer (tests, embeddings, any future turn path that skips the turn-level `:start`) got a silent drop with `done-p` never delivered and only the 20-minute idle timeout ending the turn. Terminal transitions now exist on `:idle` too (mirroring the accumulating states), so terminal events are accepted from any state and `done-p` is always delivered.
- A mid-stream OpenAI chat-completions SSE error chunk carrying its status under a TOP-LEVEL `http_status` key (`{"http_status": 529, "error": {...}}`) now keeps its numeric `:http-status` on the `:error` event instead of losing it: `emit-chat-error!`'s status extraction previously read `:status`/`[:error :status]`/`[:error :http_status]` only, while the anthropic `"error"` branch also reads top-level `:http_status` — so a transient 5xx/overload delivered that way was classified `:unknown` and NOT auto-retried. Extraction now includes the top-level location, mirroring the anthropic branch.
- A codex stream HTTP error (a 401/429/500 from the ChatGPT backend or a custom codex endpoint) now keeps its response headers on the `:error` event for diagnostics: the codex HTTP-error branch previously destructured away `:headers`/body even though the codex error emitter supports headers (used by the SSE `response.failed`/`error` branches), so a `request-id`-style header was lost while the anthropic and openai chat-completions transports kept it. The full error map now flows through, mirroring the sibling transports.
- An Anthropic streamed turn whose SSE body EOFs before `message_start` (an empty/truncated body, or a malformed stream starting with `message_stop`/an `"error"` event) now emits a `:start` event before the terminal `:done`/`:error`, matching the OpenAI chat-completions and codex transports (which already emit `:start` first when the stream never started). The `:anthropic-messages` transport previously emitted `[:done]`/`[:error]` with no preceding `:start` — the last three-transport asymmetry in the EOF-level terminal flush. Benign for the turn result (the consumer's `:start` handler is a no-op), but the provider event stream is now consistent across all three transports for malformed/truncated streams.
- A mid-stream provider error on an **error-first** stream (the error arrives before any output event) now emits `:start` before the `:error` on all three transports: the `:openai-completions` error emitter (`emit-chat-error!`) and the `:openai-codex-responses` error emitter (`emit-codex-error!` — including the codex HTTP-error and exception paths, which share it) previously emitted `[:error]` with no `:start`, and the anthropic `message_delta`-with-`stop_reason` terminal emitted `[:done]` with no `:start` when the stream's first event was a `message_delta` (review 50 tested `message_stop`-first and empty-body, not `message_delta`-first). All three transports now emit `:start` once before any terminal/error event when the stream never started — the last `:start`-before-terminal gaps in the review-50 class.
- A stream-read exception on the `:anthropic-messages` and `:openai-completions` transports (a connection reset or similar failure before any output event, e.g. on the first read) now emits `:start` before the `:error` terminal instead of a bare `[:error]`: the outer catch blocks previously routed the error straight to the consumer (`stream-anthropic`'s `consume-fn` / `stream-openai`'s `transport/emit-error!`) with no start logic, while every in-band terminal/error emitter had already been fixed to emit `:start` first (review 50/52) — the codex catch block gets `:start` via `emit-codex-error!`. The anthropic and openai chat-completions catch blocks now emit `:start` once (compare-and-set on the started?/stream-started? atoms) before the `:error`, closing the last `:start`-before-terminal gap on all three transports.
- A `:openai-codex-responses` stream-read exception whose ex-data carries response headers (e.g. a status + `x-request-id` from a proxied error) now keeps them on the `:error` event: the codex catch block previously destructured away `:headers` from `exception->error` and called the headers-less arity, dropping them — the same class already fixed for the codex HTTP-error branch (review 51) and consistent with the sibling transports.
- A `:openai-codex-responses` mid-stream SSE error (`response.failed`/`error`) is now captured exactly once instead of twice: the raw SSE line was previously captured by the stream dispatcher AND the constructed `:error` event was captured again by the error emitter — two `:on-provider-response` callbacks per error, while the `:anthropic-messages` and `:openai-completions` transports capture the raw line only. The raw capture is now skipped for the error event types, so codex captures the constructed `:error` once (matching its own HTTP-error path); non-error lines are still captured raw. The capture payloads are now consistent for the same error class across all three transports.
- Anthropic streamed `"redacted_thinking"` delta events are now skipped by an explicit transport branch rather than an implicit shape dependency: the skip previously worked only because `redacted_thinking_delta` currently carries no `:text` key, so a future delta carrying `:text` (or a renamed payload field) would have emitted a phantom `:text-delta` for a block whose start/stop are already skipped. The delta skip is now explicit and shape-independent, mirroring the block's start/stop skip — no unbalanced block events possible.
- A mid-stream Anthropic SSE `error` event (the documented `{"type":"error","error":{...}}` shape — e.g. `overloaded_error`/rate-limit during a stream) now surfaces as an `:error` event and terminates the turn instead of being silently consumed: previously no `:error` event reached the consumer and no terminal `:done` was emitted, hanging the turn until the 20-minute `llm-stream-idle-timeout-ms` with a misleading timeout. The OpenAI chat-completions transport received the same fix — a mid-stream SSE error chunk (`{"error": {...}}` with no `:choices`) previously no-oped and could hang the turn identically; the codex transport already handled both shapes. The termination is now exact on all three transports: once the stream has terminated, **no further event of any kind is emitted** — exactly one terminal event (`:error` or `:done`) per stream, and a trailing SSE event after the error (a `content_block_stop`/`content_block_delta`/`content_block_start`, a `message_delta` carrying `stop_reason`, `message_stop`, a `:choices` chunk, a `[DONE]`/finish chunk, a codex `response.output_text.delta`) or a post-error stream-read exception is a full no-op. The whole SSE dispatch is short-circuited on the `done?` flag (the non-terminal branches — which previously could still emit `:text-end`/`:text-delta`/`:thinking-delta`/`:text-start`/structured-output results after an `:error` — were hardened in a follow-up review).
- A streamed Anthropic turn ending via `message_stop` **without** a preceding `message_delta` carrying `stop_reason` now records the tokens/cost accumulated from `message_start` (input + cache reads/writes; output stays 0) instead of silently recording zero usage and cost: the `message_stop` terminal `:done` previously carried no `:usage`, so any Anthropic-compatible endpoint that omits `message_delta` (or sends it without `stop_reason`/`usage`) — including DeepSeek's streaming path — produced a usage-less done even though the input/cache tokens were already accumulated.
- A mid-stream Anthropic SSE `error` event carrying its status under a `status` key (e.g. `{"type":"error","error":{"status":529,...}}`, or a generic message plus a `status` key) now keeps its numeric `:http-status` on the `:error` event instead of dropping it: the anthropic stream's status extraction previously read `[:error :http_status]`/`:http_status` only, so a transient mid-stream 5xx/overload delivered under `status` was classified `:unknown` and NOT auto-retried. Extraction now mirrors the OpenAI transports (`:status`/`[:error :status]`/`[:error :http_status]`, numeric `>= 400` only; non-numeric statuses are dropped).
- A streamed Anthropic or OpenAI chat-completions turn whose stream ends without an in-band terminal event now terminates cleanly with a `:done` instead of hanging until the 20-minute idle timeout: the `:anthropic-messages` transport (a stream that EOFs without `message_stop` / `message_delta`-with-`stop_reason` / an `"error"` event — e.g. a DeepSeek stream whose endpoint omits `message_stop`, directly relevant since DeepSeek's streaming path is unverified) and the `:openai-completions` transport (a final chunk carrying `finish_reason` but no trailing `[DONE]`, or a `[DONE]` with no prior `finish_reason` chunk) previously emitted no terminal event at all. Both transports now flush the terminal `:done` at EOF exactly like the codex transport already did — with the pending finish reason or `:stop`, and the accumulated/last-seen usage — so a truncated/non-conforming stream always terminates instead of hanging.
- An OpenAI chat-completions stream's terminal `:done` now carries the provider's usage whenever a usage chunk was seen, and a stream whose provider omits the usage chunk entirely (ignoring `stream_options.include_usage` — common for local proxies / third-party OpenAI-compatible endpoints) terminates with a usage-less `:done` recording zero usage/cost, the documented consequence for usage-omitting endpoints. Previously the zero-usage behavior on usage-omitting endpoints was undocumented (the review-47 zero-usage fix named only the anthropic `message_stop` path), and the trailing-`[DONE]`-flushed `:done` always passed usage nil even when a usage chunk had been accumulated.
- Anthropic streamed `"redacted_thinking"` content blocks (Anthropic's first thinking block in extended-thinking streams, carrying opaque base64 redacted content) are no longer mislabeled as text: their start/stop previously fell to the default `:text-start`/`:text-end`, creating a phantom empty text block and mislabeling a thinking-family block stop as text — the same mislabel class already fixed for `"thinking"` blocks. The blocks are now skipped entirely (no start/stop/delta events), so no phantom text block and no mislabeled marker appears; not reachable on the DeepSeek provider (its compat table does not support redacted-thinking blocks).
- A consumer exception while processing the Anthropic `message_stop` terminal `:done` (e.g. a statechart dispatch failure in the `:turn/done` send) no longer emits a second `:error` terminal: the terminal emission now sets the `done?` flag before the structured-output-result emissions and the `:done` consume — mirroring every other terminal path across the three transports — so the exception is swallowed by the stream's `done?`-guarded catch instead of producing the double-terminal class eliminated in earlier reviews.
- Anthropic streamed `thinking` content-block stops now emit `:thinking-end` instead of a mislabeled `:text-end` (tool_use stops still emit `:toolcall-end`, text stops `:text-end`). The turn accumulator's dedicated `:on-thinking-end` handler was dead code for the anthropic path, so the last-provider-event diagnostic marker mislabeled DeepSeek thinking-block stops (returned live 2026-08-09) as text.
- A session running a **built-in** model no longer inherits the auth config of a custom `models.edn` provider literally named the same (`anthropic`/`openai`): registry auth (custom headers, `:no-auth-header`, api-key spec) is now resolved only for custom models, so a built-in same-named session resolves only its own env/OAuth instead of sending the custom provider's key/headers to the built-in's endpoint. Symmetrically, a custom provider named `anthropic`/`openai` never receives the built-in same-named OAuth credential. This closes the provider-name-collision class at the session request-options layer (already closed at the transport, capability-inference and session-data layers).
- A mid-session provider switch (`/model` or a session profile changing the model) no longer reuses the previous provider's session-stored runtime API key: the key recorded from a prior turn is now scoped to the provider it was resolved for, and a switch to a different provider resolves the new provider's own auth (registry `:auth`/OAuth) instead of injecting the prior provider's raw key spec, literal key, or OAuth token into the new provider's endpoint — the same cross-provider credential-disclosure class already closed for the env-var fallback and OAuth content-sniffing. The reuse check also requires the built-in/custom origin to match (`:custom?` origin tag): a custom `models.edn` provider literally named `anthropic`/`openai` (same session provider string as the built-in) can no longer reuse a key recorded for the built-in same-named origin — e.g. a built-in OAuth token sent as plain `x-api-key` to the custom provider's third-party endpoint — and vice versa. The stored key is no longer a self-perpetuating fixed point either: a `models.edn` `:auth` change (or OAuth refresh) wins over the stale stored spec, while a key that exists only in session data (e.g. RPC/extension-threaded) still keeps same-provider same-origin turns working across continuations.
- OpenAI OAuth-backed selection of `gpt-5.6` now fails explicitly unless an evidenced supported ChatGPT/Codex alias or alternate OAuth-compatible transport is added later. It no longer routes to the ChatGPT/Codex backend with the literal `gpt-5.6` id, which that backend rejects for ChatGPT accounts, and no longer silently falls through to the catalog chat-completions transport. `gpt-5.5` continues to use the OAuth/Codex path.
- The `:anthropic-messages` HTTP-400 compatibility retry no longer misclassifies a keyless custom provider whose custom `:headers` reproduce the Claude Code CLI marker set (`Authorization: Bearer …` + `user-agent: claude-cli/…` + `x-app: cli`) as a genuine OAuth request. The `:without-all-betas` fallback decision now uses the transport's computed OAuth state (built-in Anthropic model + OAuth-shaped key) instead of content-sniffing the merged headers, so such a request gets its beta headers stripped on the retry like any other non-OAuth request instead of retaining them, repeating the same 400, and hard-failing.
- OpenAI requests now fail fast with a clear error when the selected model cannot be resolved to a model definition with a valid id (for example an unknown or not-yet-loaded model key). Previously an unresolved model was sent to the provider as `model: null`, which never responded and appeared to hang.
- Transient OpenAI server errors delivered as a mid-stream `error`/`response.failed` event without an HTTP status (the canonical "An error occurred while processing your request … You can retry your request … Please include the request ID …" message, and `server_error`/"internal server error" wording) are now classified as retryable provider-unavailable errors and go through automatic provider-boundary retry instead of failing the turn immediately.

### Changed
- The resolver-facing model catalog's `:configured?` reference flag no longer counts a custom provider with only incidental custom `:headers` (e.g. `X-Client`, no resolvable `:api-key`) as configured. Keyless now mirrors the shared request-time `no-auth?` predicate — a recognized auth header (`x-api-key`/`authorization`, case-insensitive) among custom `:headers` with no resolvable key, or `:auth-header? false` — so the model picker agrees with the per-request "Missing API key" fast-fail such a provider raises instead of advertising it as configured.
- A custom-provider `:api-key` spec with an empty variable name (`"env:"` / `"env: "`) is now a config error naming the literal spec ("api-key spec \"env:\" names an empty environment variable (use \"env:VAR_NAME\")") instead of an unset-var lookup: the empty-string env var is never read, and the misleading "environment variable  is unset" (blank variable name) message is no longer produced.
- Custom-provider `env:` API keys (`:auth {:api-key "env:VAR"}`) are now re-read on every request instead of being snapshotted when `models.edn` loads: exporting the variable after psi has started (or changing it in a different shell) is picked up by the next request without a reload. If the variable is unset when a request is made, the custom-provider missing-key error names it (e.g. "environment variable DEEPSEEK_API_KEY is unset — env: keys are re-read per request") instead of pointing back at the `models.edn` `:auth` block the user already configured. The resolver-facing model catalog's `:configured?` reference flag reflects this request-time resolvability: an `env:` spec whose variable is unset at catalog read time reports the provider as not configured (matching the per-request missing-key error), and exporting the variable flips the flag to configured without a reload — the pre-review-26 semantics, restored after the raw-spec storage change briefly made the flag report "a key spec was declared" rather than "a key will resolve". These `:configured?` semantics apply to **custom providers only**: built-in catalog models always report `:configured? true` — a built-in has no registry `:auth` entry and the flag has no OAuth context, so psi cannot know from the catalog alone whether `ANTHROPIC_API_KEY`/`OPENAI_API_KEY` is set or an OAuth login exists; the per-request missing-key error is the authoritative signal for built-ins.
- RPC now streams session-scoped events (`assistant/*`, `tool/*`, `session/updated`, `footer/updated`, `session/resumed`, `session/rehydrated`) only for the connection's currently focused session; background sessions no longer push their activity over the wire. Cross-session events (`context/updated`, `ui/*`, `command-result`, `error`) continue to emit regardless of focus; cross-session command-results carry their switch target under `:target-session-id` (not a bare `:session-id`) so the structural focus gate never suppresses them. Refocusing a session rehydrates its full current content via the existing navigation path, so no information is lost.
- Custom-provider API-key resolution is now provider-scoped for the `:anthropic-messages`, `:openai-completions` and `:openai-codex-responses` transports: a custom provider with no configured key fails fast with a provider-scoped "Missing API key for provider \<name\>" error instead of silently falling back to the `ANTHROPIC_API_KEY`/`OPENAI_API_KEY` env var, which previously could leak your Anthropic or OpenAI key to a third-party endpoint. Built-in Anthropic and OpenAI models still use the env-var fallback. Keyless local/custom-header auth remains supported via `:auth-header? false`/`:no-auth-header`, or a recognized auth header (`x-api-key`/`Authorization`, case-insensitive) among custom `:headers`. Custom `models.edn` providers are now origin-tagged, so this provider-scoped treatment also holds for a custom provider literally named `anthropic`/`openai` (previously such a name was misclassified as built-in and could still receive the env-var fallback and OAuth treatment).
- Custom-provider OAuth content-sniffing is closed: a custom `:anthropic-messages` provider whose configured key merely resembles an Anthropic OAuth token (`sk-ant-oat…`) now always uses plain `x-api-key` auth — the Claude Code CLI headers/system prompt are never sent to a third-party endpoint. OAuth handling remains in place for built-in Anthropic models.
- Mid-conversation system-message capability inference is now gated on built-in origin: only built-in OpenAI chat-completions catalog models get `:supports-mid-conversation-system-messages` inferred from the runtime API shape. A custom `models.edn` provider literally named "openai" (api `:openai-completions`, tagged `:custom? true`) previously received the inferred capability by name; it now must declare the field explicitly, and `:session/inject-mid-system-message` returns `:capability-not-supported` otherwise — the same provider-name-collision class already closed for env-key fallback and OAuth treatment.
- Provider request captures now redact auth headers case-insensitively on all three transports (`:anthropic-messages`, `:openai-completions`, `:openai-codex-responses` — `x-api-key`, mixed-case `Authorization`, `chatgpt-account-id`), so secrets carried in custom `:headers` never persist verbatim in `:on-provider-request` session captures.

### Added
- Automatic post-turn **tooling-friction analysis**: the context-manager extension now also runs a fire-and-forget, post-turn friction analyzer after every completed turn, in every session (excluding this analyzer's own helper sessions and other known helper/infra sessions such as entity-resolution helpers, as a recursion guard). It runs a single bounded, no-tools local-model helper session over the last 4 turns to detect friction fixable by tooling or dependency changes (not project bugs or feature work), deduping candidates against all open and the 20 most-recently-closed Munera tasks in the same helper session. Non-duplicate issues are capped at 2 newly created tasks per run and written as `munera/open/NNN-slug/design.md`-only tasks (clearly marked auto-generated, with friction description, evidence, and suggested change) in the analyzed session's own worktree. Every failure path (no local model, missing worktree, helper failure/timeout, malformed output) logs a diagnostic and no-ops without disrupting the turn.
- Automatic pre-turn **entity resolution**: the context-manager extension now registers a second `entity-resolution` turn augmenter (alongside `project-context`). For each eligible parent turn it runs a bounded, local-model helper session — created with the existing `bash` tool only — that applies the `entity-resolution` skill's method to the user text plus a rendered conversation-history excerpt, and injects any confidently-resolved `surface → canonical (evidence)` mappings as a `Resolved entities` context block before the current user message. It selects a single top-ranked local model (strong `:locality :local`, low latency, zero/low cost; no cloud fallback), tracks and cleans up its helper sessions to avoid recursion, and returns a well-formed no-op for helper sessions, blank cwd, slash-command-only prompts, no confident mapping, no local model, or failed/timed-out helper runs. Non-interactive and data-only; never mutates the submitted prompt.
- Extension API groundwork for pre-turn request augmentation: privileged extensions can register turn augmenters via `:register-turn-augmenter` when granted `:psi.capability/turn-augmentation`; the prompt lifecycle now runs an explicit pre-turn augmentation barrier, invokes authorized live providers at the runtime effect boundary, records provider diagnostics/results, and renders accepted augmentation records as turn-scoped context before the submitted user message. The context-manager scaffold now registers a minimal `project-context` augmenter that reports the effective working directory when available.
- New **ramora** extension: injects the Ramora protocol (lambda-form project knowledge organization) into the system prompt as a prompt contribution, following the same static-at-init pattern as munera and mementum. Priority 52, section "Ramora Protocol".
- New `advertise` field for skills and workflows controls whether they appear in the model's system context. Skills use `advertise: false` in `SKILL.md` frontmatter; EDN workflows use top-level `:advertise false`; `.md` single-step workflows use `advertise: false` frontmatter. Default is `true` (only the literal `false` hides; typos stay advertised). `advertise: false` affects the system-context listing only — the skill/workflow stays registered and remains invocable: a hidden **skill** via `/skill:name` and direct file read; a hidden **workflow** via `/delegate <name>` and as a workflow sub-step (it also still appears in the user-facing `/delegate list`, a listing/discovery surface rather than an invocation path). For skills it composes with the existing `disable-model-invocation` flag (hidden if either is set). The workflow-internal `review-*`, `task-*-review`, and `issue-*` skills and the sub-only workflows (`*-core` review loops, `*-final-summary`/`*-implement-pass` steps, prompt sub-reviews, `*-in-worktree` handoff wrappers, and modular `gh-*` sub-steps) are now marked `advertise: false` so they no longer add system-context noise. See [`doc/workflows.md`](doc/workflows.md).
- Custom/local model definitions can opt into textual tool-call recovery with `{:capabilities {:textual-tool-calls #{:xml}}}`. This compatibility path converts strict `<tool_call><function=...><parameter=...>` assistant-text blocks from local runners into ordinary canonical tool calls while leaving malformed markup or opt-out/frontier models unchanged.
- New **context-manager** extension: scaffold extension that subscribes to `session_turn_finished` events and logs session-id and turn-id via the extension API `:log` function. Idempotent init for reload safety. No commands, tools, operations, or prompt contributions yet.
- New `sub-agent` workflow: uses the `/delegate sub-agent ...` input directly as the delegated prompt, without adding workflow-specific instructions.
- New `resolve-task-design-entities` workflow: runs the entity-resolution skill over a Munera task's `design.md`, rewriting ambiguous references to canonical project entities/paths/terms and recording unresolved ambiguity as feedback. Invokable via `/delegate resolve-task-design-entities`.
- New `entity-resolution` workflow: resolves ambiguous references in arbitrary input into concrete project entities/paths/terms, asking a focused clarification question when the mapping is not unique. Invokable via `/delegate entity-resolution`.

### Changed
- `bb commit-check:file-lengths` now scans `extensions/` as well as `components/` and `bases/` `src`/`test` paths. Explicitly recorded legacy oversized extension files are ratcheted to pass at their recorded line counts and fail if they grow; new oversized scanned files still fail at the 800-line limit.
- The default LLM stream idle timeout is now 20 minutes (`1200000` ms), up from 10 minutes, reducing false `Timeout waiting for LLM response` failures during long-running review/delegated turns.
- `task-lifecycle` now halts before plan creation and hands back to the human when the task's `design-steps.md` has one or more unchecked `SCOPE_QUESTION:` items, naming each open question, instead of silently defaulting the scope decision. A new `check-scope-question-status` gate runs immediately after `review-task-design` and scans `design-steps.md` by content (independent of review convergence, since a converged design review can still leave a `SCOPE_QUESTION` unchecked). To resume, decide the scope question, record the decision in `design.md`, check the `- [x] SCOPE_QUESTION:` item, and re-invoke `task-lifecycle` (a stateless re-scan). When a run is both non-converged and has an open scope question, the scope handback wins over the generic design-convergence handback.
- `task-lifecycle` now stops and hands back to the human at the design or plan stage when the corresponding review does not converge, instead of hard-failing the run. At the design boundary, after the scope-question gate proceeds, `check-design-review-status` proceeds to `create-task-plan` on `PASS_STATUS: REVIEW_COMPLETE` or routes to a `final-summary-design-not-converged` handback on `PASS_STATUS: ACTIONABLE_FEEDBACK` (no knowledge extraction, no plan creation); an analogous `check-plan-review-status` gate proceeds to `implement-task` or routes to `final-summary-plan-not-converged`. The `review-task-design`/`review-task-plan` converged final summaries now also emit a `PASS_STATUS: REVIEW_COMPLETE` line, which changes their standalone `/delegate` result text. The non-converging handback summary (`final-summary-not-converged`, `PASS_STATUS: ACTIONABLE_FEEDBACK`) is surfaced only through the `task-lifecycle` design/plan gate; a **standalone** non-converging `/delegate review-task-design`/`-plan` run now yields **empty** result text (the converged `final-summary` stays ordered last and is never reached), instead of the previous hard failure with `:reason :iteration-exhausted`.
- `review-task-plan` (invokable via `/delegate review-task-plan`) now runs its ambiguity and inconsistency checks as two prompts in one shared multi-prompt `plan-review` session, then performs one batched `plan-follow-up` for the whole review pass, mirroring `review-task-design`. The workflow deliberately changes from interleaved per-aspect follow-up (with a trailing `clarity-status` step) to batch-review-then-follow-up; the final summary reads each aspect through per-prompt output refs, and post-drain routing reuses `workflow/pass-feedback-routing` over the two per-prompt replies. The five-total-pass loop bound is unchanged.
- `review-task-design` now runs architectural-fit, ambiguity, and inconsistency checks as three prompts in one shared multi-prompt `design-review` session, then performs one batched `design-follow-up` for the whole review pass. The workflow deliberately changes from interleaved per-phase follow-up to batch-review-then-follow-up, final summaries read each phase through per-prompt output refs, and `workflow/pass-feedback-routing` now validates every review reply's `PASS_STATUS: ACTIONABLE_FEEDBACK|REVIEW_COMPLETE` line before routing.
- Implementation review profiles delegated through `review-task-implementation` may now enter the shared `review-step` review phase up to 10 total times (initial review plus follow-up-driven re-reviews) before the workflow iteration guard fails. `review-task-design` now repeats full architecture/ambiguity/inconsistency passes up to 3 total passes, and `review-task-plan` repeats full ambiguity/inconsistency passes up to 5 total passes; both finish the current pass before restarting and fail through the workflow iteration guard if the final allowed pass still finds actionable feedback.
- Built-in deterministic workflow marker routing is now exposed as the generic `workflow/exact-marker-routing` operation. The previous workflow-specific registered operations `workflow/proof-sync-disposition-routing` and `workflow/validation-capture-disposition-routing` have been removed; the simplification workflows now pass their marker labels and allowed route labels as authored workflow arguments.
- `reduce-incidental-complexity` and `reduce-architectural-complexity` now harden target-present proof gates: downstream task identity flows through deterministic `munera_task_path` extraction, generated tasks create committed `coverage-map.md` proof scaffolds, Gordian JSON/EDN artifacts are parse-checked after capture, validation/proof failures route through deterministic disposition operations, proof-sync must reach a clean fixed point before final success, and terminal stops report the explicit failed gate context instead of inferring from missing artifacts.
- `task-lifecycle` now gates its trailing `extract-task-knowledge` stage on the immediately preceding `review-task-implementation` result. It invokes extraction only after `PASS_STATUS: REVIEW_COMPLETE`; otherwise it skips extraction and returns a final summary preserving the implementation-review outcome.
- `reduce-incidental-complexity`'s generated Phase-1 burden-reduction acceptance is now a sound per-unit relocation-guard ceiling instead of the previously-emitted net-sum gate. The old A2 demanded the *sum* of `lcc-total` across the metric-derived touched set strictly decrease (`sum after < sum before`) — provably unsatisfiable for a genuine decomplecting extraction (splitting one tangle into N seams is sub-additive, so the sum can rise even as every piece is simpler), which blocked legitimate simplifications. A2 now requires every new or below-ceiling physical after-row `u` to satisfy `after(u) < B`, where `B := before(target)` is read from the committed `before-local.json` baseline; the target unit's own reduction is governed by the existing A5 check. This rejects merely relocating a tangle into a new seam or a sibling while admitting genuine decomplecting work.
- `reduce-incidental-complexity` now exposes its generated task lifecycle as explicit workflow phases and enforces a pre-simplification characterization-test-net gate before implementation. Target-present runs review the generated design/plan, record a task-local `characterization-baseline.edn`, iterate coverage review/fix until nominal/edge/boundary behavior is sufficiently characterized and green, then run a committed-plus-uncommitted diff gate that allows only tests, task artifacts, docs, and explicitly justified minimal testability seams before simplification. No-target runs still stop directly after selection with no task or downstream gate steps.
- Built-in slash commands now appear consistently in both the TUI and Emacs autocomplete: the backend is the single authoritative source of the built-in command surface (names + descriptions), exposed via the `:psi.agent-session/builtin-command-specs` graph attribute, and both UIs consume it the same way they already consume extension commands. Previously the built-in command lists were hardcoded separately in the TUI and Emacs and had drifted, so commands such as `/reload-models`, `/reload-prompts`, `/reload-extension-installs`, `/speed`, `/effort`, and `/project-repl` were missing from one or both autocompletes; they now show up automatically. The Emacs `psi-emacs-slash-command-specs` `defcustom` is now a user override/supplement (default trimmed to the Emacs-only `/skill:` affordance) — backend built-in descriptions win on any name collision.
- Extension `tool_result` events fired on the interactive/batch tool execution path now carry the parsed tool arguments under `:input`, matching the data-driven plan path; previously `:input` was present only on the plan path, so a handler reading it silently received `nil` on the interactive path.
- Extension `tool_result` handler overrides now coerce `:content` to normalized content-blocks and `:is-error` to a strict boolean — the same coercions applied to the inbound payload; previously an override's raw `:content`/`:is-error` values were copied onto the result unchanged, bypassing normalization.

### Fixed
- `review-task-implementation` review steps now disable extended thinking in the shared `review-step` workflow, preventing thinking-heavy/local model runs from exhausting the output budget before emitting the required `PASS_STATUS` marker.
- Emacs session rehydration now restores assistant tool-call and `toolResult` transcript entries as tool rows instead of rendering tool output as plain `ψ:` assistant messages. This fixes workflow child sessions opened from `/tree`/session switching, where completed tool calls from delegated review attempts were previously shown as ordinary psi output.
- `auto-session-name` now ignores delegated workflow, workflow-step, nested workflow, and helper sessions. Automatic naming remains limited to top-level user-interactive sessions, avoiding wasted helper model calls and accidental workflow child-session renames.
- `/login <provider>` in the Emacs (RPC) UI now shows the "paste the authorization code" instruction. The RPC login handler emitted the authorize URL and the paste prompt as two consecutive `assistant/message` frames; the Emacs frontend coalesces consecutive assistant messages, so the second (the instruction) was dropped and the login appeared to hang with no prompt. The URL and instruction are now emitted as a single combined message (matching the TUI), so the next-step instruction is always visible.
- Anthropic OAuth (Claude Pro/Max) requests work again. Anthropic now requires every OAuth-authenticated request to carry the Claude Code identity as its first `system` block; without it the API rejects the request with an HTTP 429 `rate_limit_error` (which surfaced as an auth/"invalid credentials" failure). psi now injects `"You are Claude Code, Anthropic's official CLI for Claude."` as the first system block whenever the resolved credential is an OAuth token, preserving any caller system prompt after it. API-key requests are unchanged. Separately, the default OAuth client id is restored to the registered Anthropic client (`9d1c250a-…`) with scopes `org:create_api_key user:profile user:inference` (the prior `a473d7bb-…`/`user:inference user:file_upload` defaults were undocumented), and the obsolete legacy-client refresh fallback is removed. The `PSI_ANTHROPIC_OAUTH_CLIENT_ID`/`…_SCOPES` overrides are unchanged.
- Standalone `/delegate review-task-design` no longer fails IR compilation with a self-reference error. The wrapper now runs `review-task-design-core` in one delegate step and checks the yielded status in a following invoke step, so all status/summary references target a prior step.
- The **dev-http** renderers now fail loud on wrong-shaped `:data` instead of silently degrading. A bare string (e.g. a Clojure-syntax string passed by mistake) to `:hiccup` previously rendered as a literal text node; similar mismatches to `:markdown`/`:table`/`:vega`/`:mermaid`/`:file` produced empty or broken output. Each renderer now validates its expected shape and returns a `400` naming the renderer, the expected shape, and the actual type. (`:hiccup` accepts a vector/array or seq of elements.)
- The **dev-http** extension now loads via the concise psi-owned manifest form (`psi/dev-http {}}`). It had been registered only in the launcher (classpath) catalog and was missing from the runtime extension-install catalog, so a concise manifest entry was silently treated as a non-extension support dep — its `init` never ran and `/dev-http` was unrecognized. Both psi-owned catalogs now agree (asserted by the existing parity test).
- `review-task-plan` no longer fails to converge when it finds a `plan.md`↔`steps.md` inconsistency. The plan review reviews both `plan.md` and `steps.md`, but the `review-follow-up-plan` step was forbidden from editing `steps.md`, so any `steps.md` finding (e.g. `steps.md` not re-synced after a `plan.md` change) could never be resolved and was re-reported on every subsequent pass until the iteration cap. The follow-up may now read and update `steps.md` to resolve such drift (`design.md` remains read-only/upstream), letting the review loop drain its feedback and converge.
- Workflow delegate steps that target a missing or retired workflow definition now name the unresolved target in the failure: the error reads `Delegated workflow definition not found: <name>` instead of the bare `Delegated workflow definition not found`, so a stale-registry failure (e.g. running `/delegate task-lifecycle` against a process whose workflow registry predates a workflow rename) is diagnosable without inspecting run internals.
- Workflow `:invoke` steps that carry both an `:operation` and an invoke `:judge` no longer abort with `:handler-entry-state-mismatch`, and looping (REPEAT) invoke steps no longer abort with `:attempt-mismatch`. The step operation and its judge operation ran two deterministic operations against one step attempt and shared the same `:operation-*-state` phase keys, so the judge's handler-entry phase failed; the judge operation now runs under a distinct `:judge-operation-*-state` key namespace. Separately, a re-executed invoke step derived its operation's attempt id from a stale pre-attempt snapshot, which the cancellation-safe attempt guard rejected on the second pass; the step operation now uses the attempt the runtime just started. Together these unblock review workflow status gates and task-lifecycle stages that route through invoke+judge steps.
- OpenAI `gpt-5.5`/Codex usage-limit failures now enter the existing provider retry/backoff path. The retry classifier recognizes OpenAI's `The usage limit has been reached` wording as a rate-limit failure even when a streamed error omits a numeric HTTP status, and Codex streamed failure events preserve embedded status and retry headers for retry scheduling.
- Cancelling or removing delegated workflow runs now routes through canonical dispatch events and runtime cleanup effects so in-flight top-level workers are interrupted before their handles are dropped, avoiding orphaned workflow execution after the delegate tool `action=remove` management action or workflow cancellation.
- A tool-use no longer wedges a session after a turn abort. Previously, interrupting a turn (`:user-abort`) while a tool-call was still in flight recorded a synthetic `"interrupted"` result for that call while the tool *also* recorded its real result, producing two `toolResult` entries for one `tool_use` id and a provider 400 (`each tool_use must have a single result`) on every later request. The agent session now enforces at-most-once `toolResult` per tool-call-id (first-writer-wins) at the single recording chokepoint, suppressing both the in-memory record and the journal append of any later duplicate. Sessions whose journals already contain duplicate `toolResult` entries also recover: the provider-facing projection now emits at most one `tool_result` per id.
- Emacs now shows retry backoff status in the session footer while provider retry scheduling is active. Backend retry activation, changed retry metadata, and retry clear events publish `footer/updated` projections through the existing RPC progress path, so Emacs renders projected text such as `retry in 8s`, updates changed retry state, and clears stale retry text after the retry succeeds or fails.
- `psi-tool project-repl op=start` / `/project-repl start` no longer fails with a 5-second `:started-readiness` timeout for legitimate slow-booting started-mode commands, and no longer latches onto a stale `.nrepl-port` left by an earlier run. Started mode now waits up to the configured readiness timeout, removes pre-existing port files before launch, accepts only a `.nrepl-port` written at/after the launch instant, reports stale-only failures as `:phase :started-stale-port`, and destroys the launched child process if readiness fails so slow/hung starts do not leak orphaned JVMs.
- TUI built-in slash autocomplete tests now exercise the backend-provided built-in command resolver instead of passing vacuously with an empty command surface, so regressions in `/help`/`/status`/`/quit` visibility and empty-surface behavior are covered.
- Workflow runs now snapshot inherited default session details at invocation time, so still-running workflow steps are isolated from later parent-session `/model` changes or user/project default-model config edits. Nested delegated workflows inherit the delegating step's effective config via their own snapshot, and resumed blocked runs reuse their original snapshot instead of re-reading live defaults.
- Workflow step `:thinking-level` default precedence now matches `:model`: explicit step setting → inherited invoke-time snapshot → workflow file metadata → `:off`. Previously workflow file metadata could mask the invoking session's snapshotted thinking level while the model used the inherited value.
- `bb clojure:test:unit`, `bb clojure:test:extensions`, and `bb clojure:test:integration` now fall back from Scry to the previous raw Kaocha runner only when Scry itself cannot execute (for example, a CLI/adapter failure reported with `scry CLI error:`), not on ordinary test failures. Failing tests therefore surface through Scry diagnostics instead of being rerun through a different path.
- `components/project-nrepl` status now records started-mode `:readiness-timeout-ms` before waiting for readiness, so timeout/stale-port failures expose the effective timeout in status/introspection even on the throwing path.
- `components/project-nrepl` reports a distinct `:phase :started-stale-port` when a started command writes no fresh endpoint but an older `.nrepl-port` is present, including the rejected port mtime and launch-time floor in diagnostics.
- Project nREPL extension install tests now tolerate the optional started-mode opts argument passed through the `ops/start` seam, matching the real `start-instance-in!` arity and preventing false `ArityException` failures from a fixed-arity `with-redefs` stub.
- The `reduce-incidental-complexity` workflow's A2 gate now emits both the criterion and the deterministic mechanical check with the same per-unit ceiling semantics; previously one prompt section could be updated while the later “how checked” section still described the obsolete net-sum behavior.
- `.psi/workflows/task-lifecycle-in-worktree.edn` now reports the inner lifecycle as design → plan → implement → review → extract knowledge, matching the current `task-lifecycle` terminal stage instead of omitting extraction from its wrapper summary contract.
- `/delegate extract-task-knowledge` documentation now uses a generic completed-task placeholder instead of naming an in-flight open task in the standalone closed-task-only example.
