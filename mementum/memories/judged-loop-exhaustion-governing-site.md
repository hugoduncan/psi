🔁 Judged workflow-loop iteration exhaustion is governed at runtime by `workflow-judge/evaluate-routing`, NOT the statechart `:judge/signal` exhaustion guard in `statechart/compile-routing-transitions`. On `:judge/enter` the matched directive is evaluated judge-side first: `check-iteration-limit` → `:exhausted` returns `{:action :fail :reason :iteration-exhausted}` (→ `:judge/failed` → status `:failed`) and short-circuits before any `:judge/signal` is enqueued. So the statechart exhaustion guard is dead code at runtime for judged review loops — a `compile-routing-transitions`-only change to exhaustion routing is inert. Task 229 needed 5 plan-review loops to surface this; the fix threaded `:on-max-iterations` through `evaluate-routing` (the governing site) and kept the statechart edit only for two-site coherence. The judge's `routing-table` IS the full IR directive (`(:on step-def)`), so directive keys threaded by `target_ir_compiler` are available there. Prove runtime exhaustion behaviour with an integration test driving a real exhausting loop through `execute-run!` — the isolated `statechart_test` feeding `:judge/signal` directly cannot detect the governing path.
