🔁 Push-based progress/footer emission (`streams/start-progress-loop!` polling + `emit-footer-updated!`) builds its payload from **live session data at delivery time**, not a snapshot of the triggering event. So an E2E test that drives a transient state (e.g. `mark-active-retry!` → sleep → `clear-active-retry!`) with a no-op sleep-fn races the ~10ms poll loop: the state can be written *and cleared* before the loop ever polls, so every captured frame carries `nil`/empty content. This produces a false failure that looks exactly like the suspected product regression (here, a suppressed retry footer).

Fix: make the injected sleep-fn **block until the expected text is actually captured** by the emit boundary (bounded await keyed per attempt, e.g. `await-retry-footer-text!`), keeping the transient state live until the async loop catches up. Reuse this synchronization pattern for any retry/progress/footer async E2E test rather than a no-op or fixed sleep.

Corollary: derive the awaited text from the *production* format authority (e.g. `retry-display/format-relative-seconds`, `ceil`), not a hand-rolled `quot` floor — a formula mismatch makes the await fail-fast on text production never emits.
