💡 In `psi.ai.model-selection/resolve-selection`, `:locality :local` (and similar) supplied as a **strong preference** only affects *ranking among survivors*, NOT *filtering*. It does not exclude non-local candidates. So when no local model is configured but a cheap-tier cloud model survives the `:required` filter (`:supports-text`, `:latency-tier :low`, `:cost-tier #{:zero :low}` — registered anthropic/openai are `:latency-tier :low` and cheap models are `:cost-tier :low`), `resolve-selection` returns `:ok` with the **cloud** candidate as `(first ranked)`.

If local-only is a hard requirement (e.g. a per-turn blocking helper on the pre-turn critical path), preference is not enough: either add `{:criterion :locality :equals :local}` to `:required`, or guard the returned winner on `(= :local (get-in candidate [:facts :locality]))` and return nil otherwise (→ no-op / no cloud run). `auto-session-name` shares the same request shape but does not elevate local-only to a hard criterion, so it carries the same latent behaviour without it being a defect there. Test with a cloud-only catalog asserting nil — a `:select-model → nil` stub never exercises the real path. (task 238)
